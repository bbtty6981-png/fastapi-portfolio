# インフルエンサーデータ自動取得のためのスクレイピング設計書

## 1. 目的

インフルエンサーのアカウントURLを登録後、以下の情報を自動取得し、データベースをリッチ化することを目的とする。

* アイコン画像
* プロフィール情報
* フォロワー数 / フォロー数
* エンゲージメント指標（投稿数、いいね数、コメントなど）

この資料は**面談で不足した説明を補うための技術ドキュメント**として作成。GitHub にそのまま掲載可能な形式。

---

## 2. 基本方針：API優先 / スクレイピングは補助的に

プラットフォームはスクレイピングを公式に禁止している場合が多く、技術的制約もあるため、以下の優先順位で設計する。

1. **（最優先）公式API が提供されている場合 → API で取得する**
2. **（次点）サードパーティAPI が安定している場合 → サードパーティAPI で取得する**
3. **（最後）どうしても取得手段がない場合のみ → スクレイピング**

スクレイピングは補助手段であり、以下の観点で採用可否を判断する。

* 規約上の可否
* 取得できる情報の粒度
* 更新頻度に耐えられる安定性

---

## 3. 取得対象メディアごとの設計方針

### ● YouTube

* 公式 API 利用が最適
* **YouTube Data API v3** で以下を取得可能

  * チャンネルアイコン
  * 登録者数
  * 動画数
  * 再生回数
  * 最近の動画情報
* スクレイピングは不要・非推奨

### ● Instagram

* 公式 API（Graph API）は**ビジネスアカウントのみ**で個人の一般プロフは取得不可
* 一般ユーザーのデータ取得ではサードパーティ API が候補
* スクレイピングも可能だが、ブロックされやすく難易度が高い

### ● TikTok

* 公開 API は存在しない
* サードパーティ API を利用するか、スクレイピングで補完
* スクレイピングは Cloudflare 対策が強く対応難度が高い

---

## 4. スクレイピングの技術設計

APIで取得できない情報をスクレイピングで補完するための実行フロー。

### ▼ 4.1 全体アーキテクチャ

```
[URL登録] → [取得対象判定] →
  ├─API で取得
  └─スクレイピングで取得（必要な場合のみ）

→ [正規化 / 整形] → [DB 保存] → [定期更新バッチ]
```

---

### ▼ 4.2 具体的なスクレイピング処理

### ① 事前解析（必須）

1. 登録された URL から媒体を自動判別
2. 各メディアごとに HTML 構造を解析
3. 取得可能な情報・不可な情報を整理

---

### ② 取得方法の選択

スクレイピングには2種類ある。

#### 【1】HTMLベースの軽量スクレイピング

* ライブラリ：Requests + BeautifulSoup
* 取得可能：テキスト、画像URL
* 想定用途：プロフィール文、フォロワー数など

#### 【2】JavaScript レンダリング対応スクレイピング

* ライブラリ：Playwright / Puppeteer / Selenium
* SPA や JS により動的に表示される情報を取得
* 想定用途：メディアページで JS が必要な場合

---

### ▼ 4.3 メディア別スクレイピング詳細

### ● Instagram（一般アカウント）

* 公開HTML内に JSON データが埋め込まれている
* BeautifulSoup + JSON抽出で対応可

##### 取得できる情報

* ユーザーネーム
* プロフィール文
* フォロワー数
* フォロー数
* 投稿数
* アイコンURL

##### 取得困難なもの

* リーチ / インサイト系（APIでのみ取得可）
* リアルタイムのエンゲージメント（HTMLで非表示）

---

### ● TikTok

* TikTok は Cloudflare + bot 判定が厳しい
* ブラウザ自動化ツールでヘッドレスを回避しながら取得

##### 対策例

* Playwright で人間らしい挙動（遅延）をつける
* User-Agent / viewport を実ブラウザにする
* セッションCookieを定期更新

---

## 5. 取得不可能な情報の明確化

スクレイピングでは以下の情報は取得できない。

* **非公開（鍵付き）アカウントの情報**
* **インサイト / アナリティクス**（再生維持率、保存数等）
* **広告向けの詳細エンゲージメント情報**

これらは **API でのみ取得可能**。クライアントにも最初の段階で説明しておくべき項目。

---

## 6. 定期更新バッチ

インフルエンサー情報は常に変動するため、以下の仕組みを組み込む。

### ● 実行方式

* Celery + Redis
* GitHub Actions + Cron
* AWS Lambda + EventBridge

### ● 更新頻度の例

* プロフィール：1日1回
* フォロワー数：1日数回
* 投稿データ：1日1〜2回

---

## 7. リスクと対策（重要）

### ● スクレイピング規約違反リスク

→ APIがある場合は必ずAPIを使用

### ● ブロックされるリスク

→ 取得間隔をランダム化・リクエストをスロットル

### ● HTML構造の変更で動かなくなるリスク

→ “構造変化に強い”JSON抽出方式を優先

### ● 法務リスク

→ 公開情報のみ取得する、非公開情報は取得しない

---

## 8. まとめ

* API で取得できる部分は API を最優先
* 不足分のみスクレイピングで補完
* HTML変化に強い手法と Cloudflare 回避技術が鍵
